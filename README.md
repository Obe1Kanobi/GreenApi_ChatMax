# MAX Chat — веб-интерфейс для MAX на GREEN-API

Тестовое задание: пользовательский интерфейс для отправки и получения текстовых сообщений в мессенджере MAX через сервис [GREEN-API](https://green-api.com/max). Внешний вид повторяет [web.max.ru](https://web.max.ru/).

**Сценарий из задания:**

1. Пользователь вводит учётные данные GREEN-API (`idInstance`, `apiTokenInstance`).
2. Вводит номер телефона получателя и создаёт новый чат.
3. Пишет текстовое сообщение и отправляет его получателю в MAX.
4. Получатель отвечает в мессенджере MAX.
5. Пользователь видит ответ в чате.

**Полезные ссылки на документацию:**

| Метод | Назначение | Документация |
|---|---|---|
| `getStateInstance` | Проверка учётных данных при входе | [GetStateInstance](https://green-api.com/v3/docs/api/account/GetStateInstance/) |
| `checkAccount` | Номер телефона → `chatId` | [CheckAccount](https://green-api.com/v3/docs/api/service/CheckAccount/) |
| `sendMessage` | Отправка текста | [SendMessage](https://green-api.com/v3/docs/api/sending/SendMessage/) |
| `receiveNotification` | Получение входящего уведомления | [ReceiveNotification](https://green-api.com/v3/docs/api/receiving/technology-http-api/ReceiveNotification/) |
| `deleteNotification` | Подтверждение обработки уведомления | [DeleteNotification](https://green-api.com/v3/docs/api/receiving/technology-http-api/DeleteNotification/) |

Также: [Технология HTTP API](https://green-api.com/v3/docs/api/receiving/technology-http-api/) · [Идентификатор чата](https://green-api.com/v3/docs/api/chat-id/) · [Перед началом работы](https://green-api.com/v3/docs/before-start/)

## 0. Главные подводные камни

### 0.1. Несовпадение chatId (самое важное)

В MAX у чата **числовой** идентификатор вида `"10000000"`, а не номер телефона.

Отправить по номеру можно (`79991234567@c.us`), но ответ придёт с **другим** `chatId` — уже числовым. Документация прямо говорит: отправка по номеру подходит только если входящие обрабатывать не нужно. Нам входящие нужны, поэтому:

1. Пользователь вводит номер → вызываем **CheckAccount** → получаем `{ exist, chatId }`.
2. В чате храним и телефон, и `chatId`. Отправляем **только по `chatId`**.
3. Входящие сопоставляем по `body.senderData.chatId`.

```http
POST {apiUrl}/waInstance{idInstance}/checkAccount/{apiTokenInstance}
Content-Type: application/json

{ "phoneNumber": 79991234567 }
```

```json
{ "exist": true, "chatId": "10000000", "fromCache": true }
```

> ⚠️ `phoneNumber` передаётся **числом**, не строкой.
>
> ⚠️ CheckAccount работает только для номеров РФ (`7`) и РБ (`375`).
>
> ⚠️ Частые проверки (особенно несуществующих номеров) MAX может наказать временными ограничениями. Результат кэшируем, повторно для одного номера не вызываем.

### 0.2. apiUrl

В задании пользователь вводит только `idInstance` и `apiTokenInstance`, но любой запрос идёт на:

```
{apiUrl}/waInstance{idInstance}/{method}/{apiTokenInstance}
```

`apiUrl` у каждого инстанса свой и указан в личном кабинете. Решение: третье поле **«API URL»** со значением по умолчанию, спрятанное в блок «Дополнительно».

### 0.3. Очередь уведомлений FIFO

`receiveNotification` отдаёт уведомления по одному. Пока текущее не удалено через `deleteNotification`, следующее не придёт.

**Удалять нужно любое уведомление** — статусы, смену состояния инстанса, картинки, стикеры, а не только текстовые. Иначе очередь встанет на первом же «неинтересном» событии.

### 0.4. React StrictMode

В dev-режиме эффекты запускаются дважды. Без отмены получится два параллельных цикла опроса, которые будут забирать уведомления друг у друга. Нужен `AbortController` и флаг остановки в cleanup эффекта.

### 0.5. Ограничения бесплатного тарифа MAX Developer

| Ограничение | Что это значит для нас |
|---|---|
| Максимум 3 чата | При попытке написать в 4-й API вернёт ошибку **466**. Формат `номер@c.us` и числовой `chatId` считаются **разными** чатами — поэтому везде только числовой `chatId`. |
| ~100 проверок CheckAccount в месяц | Кэшировать результат, не проверять один номер повторно. При частых проверках — ошибка **469** и пауза на 2 часа. |

## 1. Подготовка

*До написания кода, ~2–3 часа.*

**Понадобятся два аккаунта MAX:**

- первый подключается к GREEN-API — от его имени идёт отправка;
- второй — «получатель», который будет отвечать (второй телефон, друг, родственник).

Без второго аккаунта последние пункты сценария не проверить.

### Шаги

1. Зарегистрироваться в [console.green-api.com](https://console.green-api.com), создать инстанс на тарифе **MAX Developer** (бесплатный). Переход в рабочее состояние — до 2 минут.
2. Авторизовать инстанс по QR-коду:
   - **на компьютере:** в кабинете выбрать инстанс → «Получить QR-код для авторизации»;
   - **на телефоне:** приложение MAX → **Профиль → Устройства → Войти по QR-коду** → навести камеру на QR на мониторе.

   > ⚠️ Перед сканированием **отключить пароль для входа в MAX** — с паролем QR-авторизация сейчас не работает.
   >
   > ℹ️ Веб-версия MAX (web.max.ru) QR сканировать не умеет — только мобильное приложение.
3. Записать `apiUrl`, `idInstance`, `apiTokenInstance`.
4. Настройки инстанса:
   - `webhookUrl` — **пустой** (иначе `receiveNotification` вернёт 400);
   - «Входящие сообщения» — включить;
   - «Сообщения, отправленные с телефона» — можно включить, пригодится.

   Или программно через `SetSettings`:

   ```json
   {
     "webhookUrl": "",
     "incomingWebhook": "yes",
     "outgoingWebhook": "yes",
     "stateWebhook": "yes"
   }
   ```
5. **Прогнать весь сценарий в Postman/curl до написания кода:**
   `getStateInstance` → `checkAccount` → `sendMessage` → ответ со второго телефона → `receiveNotification` → `deleteNotification`.
   Так будут видны реальные JSON-ответы.
6. **Проверить CORS.** Выполнить `fetch` к API прямо из консоли браузера.
   - Проходит → фронт ходит в API напрямую.
   - Блокируется → в dev настраиваем proxy в Vite, для деплоя — прокси (например, rewrites в Vercel).

   Выяснить в первый день: от ответа зависит архитектура.

## 4. Модель данных

```ts
type Credentials = {
  apiUrl: string;
  idInstance: string;
  apiTokenInstance: string;
};

type Message = {
  id: string;              // idMessage из API (или временный локальный id)
  chatId: string;
  text: string;
  direction: 'in' | 'out';
  timestamp: number;       // секунды, как в API
  status?: 'sending' | 'sent' | 'failed';
};

type Chat = {
  chatId: string;          // из CheckAccount
  phone: string;           // 79991234567
  name?: string;           // senderName из входящих, когда появится
  messages: Message[];
  unread: number;
};
```

> 💾 Чаты и сообщения сохраняем в **localStorage**. После `deleteNotification` уведомление исчезает из API навсегда — без сохранения история пропадёт при обновлении страницы.

## 5. Слой API

Файл `src/api/greenApi.ts`. Все URL строятся по шаблону:

```
${apiUrl}/waInstance${idInstance}/${method}/${apiTokenInstance}
```

| # | Функция | HTTP | Тело / параметры | Ответ | Примечание |
|---|---|---|---|---|---|
| 1 | `getStateInstance` | GET | — | `{ stateInstance }` | При входе: ждём `authorized`. Это и есть «логин». |
| 2 | `checkAccount` | POST | `{ phoneNumber: number }` | `{ exist, chatId }` | При создании чата |
| 3 | `sendMessage` | POST | `{ chatId, message }` | `{ idMessage }` | Лимит **4000** символов — валидируем на фронте |
| 4 | `receiveNotification` | GET | `?receiveTimeout=20` | `{ receiptId, body }` или пусто | Таймаут 5–60 с. Пустой ответ — **норма**, не ошибка |
| 5 | `deleteNotification` | DELETE | `/{receiptId}` в конце URL | `{ result, reason }` | Вызывать для **каждого** уведомления |

### Обработка ошибок

| Ситуация | Реакция |
|---|---|
| 401 / 403 | Разлогинить: «неверные данные или аккаунт ограничен» |
| 429 / 5xx | Повторить с паузой |
| CheckAccount: `exist: false` | «У этого номера нет MAX» |
| CheckAccount: `reason` про not authorized | «Инстанс не авторизован» |
| 466 | «Достигнут лимит чатов на тарифе Developer» |
| 469 | «Слишком много проверок номеров, попробуйте через 2 часа» |

## 6. Цикл получения сообщений

Файл `src/hooks/useNotificationPolling.ts`:

```ts
useEffect(() => {
  if (!creds) return;
  const ctrl = new AbortController();
  let stopped = false;

  (async () => {
    while (!stopped) {
      try {
        const n = await receiveNotification(creds, 20, ctrl.signal);
        if (!n) continue;                            // пусто — снова ждём
        try {
          handle(n.body);                            // наш разбор
        } finally {
          await deleteNotification(creds, n.receiptId); // удаляем ВСЕГДА
        }
      } catch (e) {
        if (ctrl.signal.aborted) break;
        await sleep(3000);                           // бэкофф при ошибке сети
      }
    }
  })();

  return () => {
    stopped = true;
    ctrl.abort();
  };
}, [creds]);
```

### Логика `handle(body)`

Пример входящего уведомления:

```json
{
  "receiptId": 1234567,
  "body": {
    "typeWebhook": "incomingMessageReceived",
    "timestamp": 1763115112,
    "idMessage": "126543123451133331119",
    "senderData": {
      "chatId": "10000000",
      "chatName": "Иван Иванов",
      "sender": "10000000",
      "senderName": "Иван Иванов",
      "senderPhoneNumber": 79876543210
    },
    "messageData": {
      "typeMessage": "textMessage",
      "textMessageData": { "textMessage": "Привет!" }
    }
  }
}
```

| `typeWebhook` | `typeMessage` | Где текст | Действие |
|---|---|---|---|
| `incomingMessageReceived` | `textMessage` | `messageData.textMessageData.textMessage` | Добавить входящее |
| `incomingMessageReceived` | `extendedTextMessage` (текст со ссылкой) | `messageData.extendedTextMessageData.text` ⚠️ *сверить с реальным JSON* | Добавить входящее |
| `incomingMessageReceived` | прочее (фото, стикер…) | — | Заглушка «[неподдерживаемый тип]» или пропуск |
| `outgoingAPIMessageReceived` | — | — | Эхо наших отправок: не дублировать, максимум обновить статус |
| остальное | — | — | Игнорировать (**но удалить из очереди!**) |

**Дополнительно:**

- `chatId` берём из `senderData.chatId`.
- Если чата нет в списке — создаём новый (имя из `senderName`).
- Дедупликация по `idMessage`: если сообщение уже есть, не добавляем.

## 7. Сценарии UI

### Экран входа

- Поля: `idInstance`, `apiTokenInstance`, свёрнутое «API URL».
- «Войти» → `getStateInstance`, во время запроса — спиннер.
- Ошибки — понятным текстом.
- Успех → сохраняем креды (`localStorage` при «Запомнить меня», иначе `sessionStorage`) → экран чатов.
- «Выйти» → очистка всего.

### Создание чата

1. Кнопка «+» / «Новый чат» в сайдбаре → поле номера.
2. Нормализация ввода:
   - убрать пробелы, скобки, дефисы, `+`;
   - ведущую `8` заменить на `7`;
   - проверить, что получилось 11–12 цифр.
3. `CheckAccount` → если `exist` — создать чат и открыть его.
4. Если такой `chatId` уже есть — открыть существующий.

| Ввод | После нормализации |
|---|---|
| `+7 (999) 123-45-67` | `79991234567` |
| `8 999 123 45 67` | `79991234567` |
| `+375 29 123-45-67` | `375291234567` |

### Отправка

- **Enter** — отправить, **Shift+Enter** — перенос строки.
- Оптимистичное обновление: сообщение сразу в ленте со статусом «отправляется».
- После ответа API → настоящий `idMessage`, статус «отправлено».
- При ошибке → «не отправлено» + кнопка повтора.
- Пустые сообщения и сообщения из одних пробелов блокируем.

### Получение

- Новое сообщение появляется в открытом чате, автоскролл вниз.
- Если чат не открыт → растёт счётчик непрочитанных, чат поднимается наверх списка.

### Слева (~320px)

- Шапка: заголовок + кнопка нового чата.
- Поиск/фильтр по списку (по желанию).
- Элемент списка: аватар-кружок (инициалы или последние цифры номера), имя или номер, последнее сообщение в одну строку с обрезкой, время, бейдж непрочитанных.

### Справа

- Шапка чата: аватар, имя, номер.
- Лента сообщений.
- Поле ввода внизу + кнопка отправки.

### Пузыри сообщений

- Исходящие — справа, своим цветом.
- Входящие — слева, светлые.
- Время `HH:MM` в углу.
- Бонус: разделители по датам («Сегодня», «Вчера»).

### Прочее

- Пустое состояние: «Выберите чат или создайте новый».
- Цвета, шрифты, скругления — снять с web.max.ru через DevTools.
- Адаптив: на узком экране показывается либо список, либо чат.

## 10. Работа с Code Assistant

- **Задачи по одному модулю**, а не «сделай мессенджер».
- **К каждой задаче — точный контракт API:** URL, метод, пример тела запроса и ответа. Лучше всего — реальный JSON из своих Postman-запросов.
- **Обязательно дать пример уведомления `incomingMessageReceived`** (раздел 6) — иначе ассистент придумает формат.
- **К задачам по вёрстке** — скриншот web.max.ru.
- **Отдельно предупредить** про StrictMode (раздел 0.4) и обязательное удаление уведомлений (раздел 0.3): это типичные места, где сгенерированный код ломается тихо.

```bash
git clone https://github.com/your-username/GreenApi_ChatMax.git
cd GreenApi_ChatMax

# Установить зависимости
yarn install

# Запустить в режиме разработки
yarn dev
```

Приложение будет доступно по адресу [http://localhost:5173](http://localhost:5173).
